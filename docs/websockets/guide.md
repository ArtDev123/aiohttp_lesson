# Прогресс экспорта — обзор и архитектура

Пошаговая реализация — в [README.md](README.md). Этот файл — **карта**: откуда берётся `book_count`, почему сокет живёт в процессе API, чего не меняем в файле экспорта.

> **Правило:** не пишите код «вперёд гайда». Сначала промежуточный статус в задаче. Потом один снимок для `GET` и для сокета. Потом `WS`. Файл по сокету не шлём.

---

## 1. Зачем этот гайд

После Celery клиент сам крутит опрос:

```text
POST /exports                         → 202 + task_id
GET  /exports/{task_id}               → PENDING
GET  /exports/{task_id}               → STARTED
GET  /exports/{task_id}               → SUCCESS, book_count
GET  /exports/{task_id}/file          → JSON
```

Между `STARTED` и `SUCCESS` на 150 000 книг проходят секунды, а `GET` всё это время молчит: `book_count` появляется только в конце, потому что задача кладёт его в `return`.

WebSocket меняет доставку, не работу. Воркер по-прежнему читает Postgres и пишет файл. API по-прежнему не собирает каталог в запросе. Клиент один раз открывает соединение и слушает:

```text
{"status": "PENDING",  "book_count": null}
{"status": "STARTED",  "book_count": null}
{"status": "PROGRESS", "book_count": 10000}
{"status": "PROGRESS", "book_count": 50000}
{"status": "SUCCESS",  "book_count": 150000, "filename": "<task_id>.json"}
```

Дальше сокет закрывается. Файл забирают прежним `GET /exports/{task_id}/file`. В кадр 150 000 книг не кладём: это скачивание, для него уже есть `FileResponse`.

## 2. Два процесса, одно хранилище

Сокет открыт в процессе Uvicorn. Задача крутится в процессе Celery. У них нет общей памяти, передать объект сокета в воркер нельзя.

```text
клиент                         app (Uvicorn)                    worker
  │  POST /exports                  │                              │
  │ ───────────────────────────────►│ delay()                      │
  │ ◄──────── 202 task_id ──────────│──────────── Redis ──────────►│
  │                                 │                              │ SELECT пачками
  │  WS /exports/{id}/ws            │                              │ update_state
  │ ───────────────────────────────►│                              │   book_count
  │                                 │ AsyncResult ◄──── Redis ◄────│
  │ ◄──── кадр PROGRESS ────────────│                              │
  │ ◄──── кадр SUCCESS ─────────────│                              │ файл на диске
  │  GET /exports/{id}/file         │                              │
  │ ◄──────── JSON файла ───────────│                              │
```

| Кто | Что делает | Чего не делает |
|-----|------------|----------------|
| воркер | пачка SQL, дописывает файл, `update_state` | не знает про сокеты |
| Redis | хранит состояние задачи | не рассылает кадры клиентам |
| `app` | читает Redis и шлёт кадр в открытый сокет | не считает каталог |
| клиент | слушает, в конце качает файл | не опрашивает `GET` статуса |

Это не «настоящий» push из воркера. API сам спрашивает Redis примерно два раза в секунду и, если снимок изменился, пишет кадр. Для одного учебного экспорта этого хватает. Отдельный pub/sub «воркер публикует, все API подписаны» — не этот урок.

## 3. Что не трогаем

| Файл | Почему |
|------|--------|
| `app/models.py`, `alembic/` | схема та же |
| `POST /exports` | по-прежнему `202` и `delay()` |
| `GET /exports/{task_id}/file` | файл не едет по сокету |
| `EXPORT_BATCH_SIZE` | пачка 1 000 уже есть |
| `task_1_client/` | отдельная задача |

`GET /exports/{task_id}` остаётся. Сокет его не заменяет для тех, кому удобнее опрос. Оба читают одну функцию снимка.

Задача экспорта **та же по смыслу**: sync-сессия, файл, `return` с итогом. Добавляется только `update_state` после пачки. Без этой строки сокет умеет показать `STARTED` и потом сразу `SUCCESS` — промежуточного `book_count` в Redis нет.

## 4. Карта API (добавка)

Сервер: `http://127.0.0.1:8080`. Старые эндпоинты не меняются.

| Метод | URL | Назначение |
|-------|-----|------------|
| POST | `/exports` | поставить задачу, `202` |
| GET | `/exports/{task_id}` | снимок статуса, в том числе промежуточный `book_count` |
| GET | `/exports/{task_id}/file` | скачать JSON |
| WS | `/exports/{task_id}/ws` | те же снимки кадр за кадром, пока не `SUCCESS` или `FAILURE` |

Авторизации нет, как в остальном уроке.

Чужой `task_id` для Celery выглядит как `PENDING` всегда: ключа в Redis нет, это не ошибка «не найдено». Сокет тогда не закроется сам. В уроке таймаут на это не ставим — клиент закрывает соединение.

## 5. Структура после гайда

Отдельной папки `app/websockets/` нет. Сокет — ещё один метод того же ресурса, рядом с `GET` статуса.

```text
aiohttp_lesson/
├── requirements.txt          # + websockets (клиент проверки)
├── app/
│   ├── tasks.py              # update_state после пачки
│   └── routes/
│       └── exports.py        # снимок + WebSocket
└── docs/
    └── websockets/           # этот гайд
```
