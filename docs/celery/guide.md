# Фоновый экспорт — обзор и архитектура

Пошаговая реализация — в [README.md](README.md). Этот файл — **карта**: зачем очередь, какие процессы крутятся, какое API добавляем.

> **Правило:** не пишите код «вперёд гайда». Сначала Redis и `ping`, потом задача экспорта, потом роуты, потом два новых сервиса в Compose.

---

## 1. Зачем третий гайд

До сих пор один запрос = одна функция, которая успевает до ответа. Для списка из трёх сидов это нормально.

Экспорт каталога — другая работа:

- может занять секунды (а в проде — минуты: много строк, файл, письмо);
- клиенту не обязательно ждать файл в том же HTTP-ответе;
- Uvicorn не должен стопориться на одном тяжёлом хендлере.

Если собрать JSON **в** `POST /exports`, воркер Uvicorn занят, пока идёт SELECT и запись на диск. При одном воркере остальные клиенты ждут.

```text
плохо (в запросе)                     хорошо (очередь)
─────────────────                     ────────────────
POST /exports                         POST /exports
  SELECT все книги                      delay() → Redis
  писать файл                           202 + task_id
  200 + файл                          клиент потом спрашивает GET
  (Uvicorn стоит)                     воркер делает SELECT отдельно
```

**Очередь** — ящик между «принять заказ» и «сделать работу». FastAPI кладёт записку, отвечает сразу. Другой процесс читает записку и работает.

## 2. Три процесса

После Docker у нас уже было два контейнера: `app` и `db`. Теперь четыре роли (локально — четыре процесса, в Compose — четыре сервиса):

```text
браузер / curl
      │
      │  POST /exports
      ▼
┌─────────┐     delay()      ┌─────────┐     задача      ┌─────────┐
│   app   │ ───────────────► │  redis  │ ──────────────► │ worker  │
│ FastAPI │ ◄─────────────── │ брокер  │ ◄────────────── │ Celery  │
└─────────┘   AsyncResult    └─────────┘    статус       └────┬────┘
      │                                                       │
      │  GET /books                                           │ sync SELECT
      ▼                                                       ▼
┌─────────────────────────────────────────────────────────────────┐
│                         PostgreSQL (db)                         │
└─────────────────────────────────────────────────────────────────┘
```

| Процесс | Что делает | Чего не делает |
|---------|------------|----------------|
| `app` (Uvicorn) | принимает HTTP, кладёт задачу, отдаёт статус и файл | не собирает каталог |
| `redis` | хранит очередь сообщений и результат задачи | не знает про книги |
| `worker` (Celery) | забирает задачу, читает БД, пишет JSON | не слушает порт 8080 |
| `db` | таблицы, как раньше | — |

Это то же правило, что в Docker: **один контейнер — один процесс**. Воркер — не «ещё один Uvicorn», а отдельная программа с своим циклом.

Redis здесь **не кэш** страниц. Он — почтовое отделение: положили письмо (`delay`), забрали (`worker`), положили квитанцию (результат).

## 3. Цепочка экспорта

```text
POST /exports
  → export_catalog.delay()
  → Redis: «сделай export_catalog»
  → 202 {"task_id": "...", "status": "PENDING"}

воркер
  → забирает сообщение
  → sync Session → SELECT books + author + genre
  → пишет exports/<task_id>.json
  → кладёт в Redis {book_count, filename}

GET /exports/{task_id}
  → AsyncResult(task_id)
  → PENDING / STARTED / SUCCESS / FAILURE

GET /exports/{task_id}/file
  → FileResponse, если файл уже есть
```

`task_id` выдаёт Celery (UUID). Мы его не генерируем руками.

## 4. Что не трогаем

| Файл | Почему |
|------|--------|
| `app/models.py` | таблицы те же, миграции нет |
| `alembic/` | схема не меняется |
| `app/repositories/` | воркер ходит в SQLAlchemy **напрямую**, sync |
| `task_1_client/` | отдельная задача |
| CRUD `/genres` `/authors` `/books` | поведение то же |

Воркер **не** использует `BookRepository` и `AsyncSession`. Celery по умолчанию **синхронный**: задача — обычный `def`, не `async def`. Sync-URL у нас уже есть — им пользуется Alembic (`database_url_sync`, `psycopg2`).

Роуты FastAPI по-прежнему async. Два мира рядом: HTTP — asyncpg, задача — psycopg2.

## 5. Карта API (добавка)

Сервер: `http://127.0.0.1:8080`. Старые эндпоинты не меняются.

| Метод | URL | Назначение |
|-------|-----|------------|
| POST | `/exports` | поставить экспорт в очередь, `202` |
| GET | `/exports/{task_id}` | статус и `book_count` (когда готов) |
| GET | `/exports/{task_id}/file` | скачать JSON |

Авторизации нет, как в остальном уроке.

## 6. Структура репозитория после гайда

```text
aiohttp_lesson/
├── .env                      # + REDIS_URL
├── requirements.txt          # + celery, redis
├── exports/                  # JSON-файлы (не в git)
├── app/
│   ├── celery_app.py         # Celery(...)
│   ├── tasks.py              # ping, export_catalog
│   ├── config.py             # + redis_url
│   ├── db.py                 # + make_sync_engine
│   ├── schemas.py            # + ExportAccepted / ExportStatus
│   └── routes/
│       └── exports.py
├── docker-compose.yml        # + redis, worker, том exports
└── docs/
    └── celery/               # этот гайд
```

`celery_app.py` и `tasks.py` на шаге 2. Роут — на шаге 4. Сервисы Compose — на шаге 5.
