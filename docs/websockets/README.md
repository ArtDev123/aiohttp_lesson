# Прогресс экспорта — WebSocket

Продолжение после Celery. `POST /exports` по-прежнему сразу отдаёт `task_id`. Статус больше не надо опрашивать `GET /exports/{task_id}` в цикле: клиент открывает сокет и получает цепочку `PENDING` → `STARTED` → `PROGRESS` → `SUCCESS`. В `PROGRESS` и `SUCCESS` есть `book_count`. Файл по-прежнему скачивается отдельным `GET /exports/{task_id}/file`.

На каталоге в 150 000 книг пачки по 1 000 длятся секунды, и счётчик в сокете реально ползёт. На трёх сидовых книгах он прыгает сразу в `SUCCESS`.

Материал разбит на этапы: теория → код → разбор → проверка.

## Как читать

1. Сначала [guide.md](guide.md) — кто пишет статус, кто толкает сокет, почему воркер сокет не держит.
2. Затем строго по порядку шаги ниже — не переходите дальше, пока не отметили «✅ Готово».

Каждый технический блок устроен одинаково:

1. **Задача** — что должно получиться и зачем шаг нужен.
2. **Теория** — концепции, без которых код «магия».
3. **Код** — что пишем в файлы.
4. **Разбор** — зачем каждая конструкция.
5. **✅ Проверка** — команды / `curl` / клиент сокета: что должно работать **сейчас**.

> **Правило:** не открывайте сокет «вперёд гайда». Сначала задача пишет промежуточный `book_count` в Redis. Потом тот же снимок читает `GET`. Потом его же шлёт WebSocket.

## Что уже должно быть

Рабочий Celery: `POST /exports` → `202`, воркер, Redis, `GET` статуса и файла. В `celery_app.py` уже стоит `task_track_started=True` — без этого не будет состояния `STARTED`.

Каталог большой: `python -m app.seed` доливает книги до 150 000. На пустой базе сокет технически жив, но прогресса не видно.

GraphQL и pytest для этого гайда не нужны. Клиент задачи 1 (`task_1_client`) не трогаем.

## Стек после этого гайда

| Компонент | Зачем |
|-----------|--------|
| FastAPI / Starlette | WebSocket уже внутри, отдельный сервер сокетов не ставим |
| Celery + Redis | воркер пишет статус, API его читает |
| `websockets` | только ручной клиент для проверки |
| PostgreSQL | тот же каталог, тот же `export_catalog` |
