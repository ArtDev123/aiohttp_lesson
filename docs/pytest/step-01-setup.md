# Шаг 1 — pytest и первый тест

**Предыдущий:** [README.md](README.md) · **Следующий:** [step-02-testdb.md](step-02-testdb.md)

## Задача

Поставить pytest, завести папку `tests/` и убедиться, что раннер находит функцию с `assert`. К приложению и к базе ещё не ходим — сначала инструмент, иначе на шаге 3 непонятно, красный pytest или красная Postgres.

---

## Теория: что такое тест

Тест — обычная функция. pytest делает три вещи:

1. Находит файлы и функции по **именам**.
2. Вызывает каждую.
3. Если внутри сработал `assert` с ложью — тест упал; если функция дошла до конца — прошла.

```python
def test_one_plus_one() -> None:
    assert 1 + 1 == 2
```

`assert` — не специальный API pytest. Это Python. pytest перехватывает падение и печатает «было / стало»:

```text
assert 1 + 1 == 3
#  2 != 3
```

Имена важны:

| Что | Правило | Пример |
|-----|---------|--------|
| файл | `test_*.py` или `*_test.py` | `test_health.py` |
| функция | `test_*` | `test_health_ok` |
| класс (если нужен) | `Test*` | `TestBooks` |

Файл `checks.py` с функцией `health_ok` pytest **не увидит**. Это не баг, а договорённость, чтобы не схватить случайные функции из `app/`.

По умолчанию pytest спускается от текущей папки. Мы ограничим его `tests/` в `pytest.ini`, чтобы он не заглядывал в `alembic/` и `task_1_client/`.

---

## Теория: зачем отдельная папка

Код приложения — `app/`. Тесты — `tests/`. Смешивать не стоит:

- в образ Docker тесты можно не копировать (их уже режет `.dockerignore` через `docs` и часто `tests` стоит добавить);
- импорты приложения остаются `from app.main import app`;
- проще сказать CI: «гоняй `pytest`».

Не кладите тесты внутрь `app/tests/`: тогда `app` станет ещё и тестовым пакетом, и `COPY app ./app` утащит их в прод-образ.

---

## 1. Дописать `requirements.txt`

В конец:

```text
pytest>=8.0
```

`TestClient` уже приезжает вместе с FastAPI (Starlette + httpx). Отдельный `httpx` в файл не обязателен. `pytest-asyncio` тоже не ставим: клиент синхронный.

```bash
source .venv/bin/activate
pip install -r requirements.txt
```

---

## 2. `pytest.ini` в корне репозитория

```ini
[pytest]
testpaths = tests
```

Одна строка: «ищи тесты здесь». Без неё `pytest` начнёт обход с `.` и может споткнуться о старые кэши или скрипты.

---

## 3. `tests/test_smoke.py`

```python
def test_one_plus_one() -> None:
    assert 1 + 1 == 2
```

Никакого FastAPI. Если этот файл красный — ломается установка или запуск, не приложение.

---

## Разбор команды

```bash
pytest
```

То же самое, что `python -m pytest`. Запускайте из **корня** репозитория: иначе не найдётся `pytest.ini` и пакет `app`.

Полезные флаги (запомните, на шаге 3 пригодятся):

| Флаг | Зачем |
|------|--------|
| `-q` | короче вывод |
| `-k health` | только тесты, в имени которых есть `health` |
| `-x` | остановиться на первом падении |
| `-vv` | показать полный diff |

Windows: та же команда из активированного venv.

## ✅ Проверка

```bash
source .venv/bin/activate
pytest
```

| ☐ | Действие | Ожидаемый результат |
|---|----------|---------------------|
| ☐ | `pip install` | в выводе есть `pytest` |
| ☐ | `pytest` | `1 passed`, собрали `tests/test_smoke.py` |
| ☐ | сломать assert (`== 3`) и снова | `1 failed`, в diff видно `2 != 3` |
| ☐ | вернуть `== 2` | снова зелёный |

Сервер (`python -m app.main`) для этого шага **не** нужен. Если он крутится на 8080 — не мешает: pytest его не вызывает.
