# Шаг 2 — Промежуточный `book_count` в задаче

**Предыдущий:** [step-01-setup.md](step-01-setup.md) · **Следующий:** [step-03-snapshot.md](step-03-snapshot.md)

## Задача

После каждой пачки писать в Redis, сколько книг уже попало в файл. Итог задачи не меняется: `return` по-прежнему `book_count` и `filename`, когда файл дописан. Сокета на этом шаге нет — прогресс смотрим тем же `GET`, но он пока **не** отдаёт промежуточное число. Это поправит шаг 3. Здесь важно увидеть в логе воркера, что состояние `PROGRESS` вообще пишется.

---

## Теория: `STARTED` не знает про книги

`task_track_started=True` уже включён. Воркер при старте задачи сам ставит `STARTED`. В этом состоянии в Redis нет числа книг: Celery кладёт туда pid процесса, не наш счётчик.

`book_count` появляется только если задача положит его сама:

```python
self.update_state(state="PROGRESS", meta={"book_count": book_count})
```

`PROGRESS` — не встроенное имя вроде `SUCCESS`. Это наша строка. Backend сохраняет `meta` как результат «на сейчас». Следующий `update_state` затирает предыдущий meta. Финальный `return` затирает meta ещё раз и ставит `SUCCESS`.

Поэтому в meta на середине **нет** `filename`: файла ещё нельзя качать, туда пишется JSON. Имя файла клиент увидит в кадре `SUCCESS`.

---

## Теория: пачка, не строка

`update_state` ходит в Redis. После каждой из 150 000 книг это 150 000 записей в backend и 150 000 поводов дёрнуть сокет. Пачка и так равна `EXPORT_BATCH_SIZE` (1 000). Один `update_state` на пачку — 150 записей на весь каталог. Счётчик на клиенте прыгает на 1 000, не на 1. Это и есть прогресс.

Вызов ставим после цикла по `rows`, когда `book_count` уже увеличен. Не внутри `for book in rows`.

---

## 1. Правка `app/tasks.py`

В `export_catalog`, сразу после `last_id = rows[-1].id` и **до** `session.expire_all()`:

```python
                last_id = rows[-1].id
                self.update_state(
                    state="PROGRESS",
                    meta={"book_count": book_count},
                )
                session.expire_all()
```

Остальное тело задачи не переписывайте. `return {"book_count": book_count, "filename": path.name}` остаётся в конце.

### Разбор

`self` есть, потому что задача объявлена `@celery_app.task(bind=True)`. Без `bind=True` метода `update_state` нет.

`state="PROGRESS"` не завершает задачу. Воркер продолжает цикл `while`. Если после этого вылетит исключение, Celery сам поставит `FAILURE` — вручную его писать не нужно.

`expire_all()` на месте: он сбрасывает объекты SQLAlchemy после пачки, чтобы сессия не держала 150 000 книг в памяти. К Redis он не относится.

Воркер загружает код при старте. После правки процесс нужно перезапустить, `--reload` у Celery нет:

```bash
# в терминале воркера: Ctrl+C, затем снова
celery -A app.celery_app worker --loglevel=info
```

В Compose: `docker compose restart worker`. Если код копируется в образ на сборке, а не томом — сначала `docker compose build worker`.

## ✅ Проверка

Новый экспорт:

```bash
curl -s -X POST http://127.0.0.1:8080/exports
```

Пока `GET` не доработан, промежуточное число в нём можно не увидеть: старый хендлер читает результат только при `SUCCESS`. Смотрите лог воркера. В строках задачи не должно быть исключения из `update_state`. В конце — `succeeded`.

Проверка через Redis не обязательна. На шаге 3 тот же `book_count` появится в `GET` ещё до конца файла.

| ☐ | Проверка |
|---|----------|
| ☐ | воркер перезапущен уже с новым `tasks.py` |
| ☐ | `export_catalog` доходит до `succeeded` |
| ☐ | `GET` в конце по-прежнему показывает `SUCCESS` и полный `book_count` |
| ☐ | `update_state` стоит один раз на пачку, не на каждую книгу |
| ☐ | сокета ещё нет |
